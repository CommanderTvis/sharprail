# Plugin isolation channel

## Responsibility

The trusted side's half of the isolated runtime that does not depend on what a plugin is: the channel, the handles
lent across it, and the process at its other end. [Security.SPEC.md](../SharpRail.Plugins.Api/Security.SPEC.md) under
"The channel and the runner process" states the protocol and the process rules; this project implements them.

- `IsoFrame` and `IsoCodec.Generated.cs` (from `scripts/generate-rpc.cs`), `IsoWire` (framing and limits).
- `FdTransport`: the framed stream and its descriptors, a Unix socket with SCM_RIGHTS or a Windows named pipe with
  handles duplicated into the runner. `FdTransport.Loopback` gives the checks a host end and a raw stream.
- `IsolationPeer`: one end of the channel, the same code on both sides (`IsolationRole` decides id parity and
  whether descriptors are accepted). `HandleTable` holds what this side lent, with tombstones.
- `ChildProcess`: spawn with exactly the channel, null standard input and a rate-limited log pipe; exit watch;
  reaping; kill of the session's group when the runner exits or is killed, or of the job. `RunnerSession`: the host's hold on one runner, with the handshake, and the
  kill on a protocol violation.
- `RunnerProbe`: the member ids of the runner's `probe echo` mode. `RunnerPlugin`: the members of its `plugin` mode
  (activate the UI half on a context, dispose it, store a mirrored value) and their arguments.
- `IsolatedUI.cs`: `IIsolatedUIHost`, which the host implements, opens a client's `IIsolatedUISession` with an
  external plugin's process: what the activation registered, the later calls on the context in arrival order
  (`IsoUICall`, answered or one-way), the plugin's callbacks and the mirror.
- `Surfaces.cs`: the surface protocol (Security.SPEC.md, UI halves): the messages that open, size, feed input to,
  acknowledge and close a surface, dismiss its popups and push the kit theme, a popup's or dialog's place
  (`SurfacePopup`, a dialog with its plain title), the cursor over a top-level (`SurfaceCursor`), a focused text
  field's caret (`SurfaceIme`), input method composition and a dialog's close request as input kinds, the
  frame header with its moves and tiles and the popup it belongs to, the caps (`SurfaceLimits`), `SurfaceFrames`
  and `SurfaceFrameState` (the caps a frame message is held to, by the host's relay and again by a remote client,
  with the keyframe a client asks for after it lost what it held), `SurfaceState` (a surface's frames and its open
  popups': numbers from 1 never reused, at most 8 open, places and sizes in range, frames only for an open popup, a
  title only on a dialog, at most 128 characters and none a control character, a cursor shape from 0 to 63 and a caret
  in range, each on the surface or an open popup),
  `SurfacePixels` (moves, applied the same way on both ends), `IPluginSurface` (a client's end of one surface, with
  the number the host gave it) and `IPluginSurfaceService` (a client context's surfaces). `TileCodec`: one colour as 4 bytes, else
  QOI without its header; decoding refuses short, long or malformed data. `IsolationPeer.OneWay` carries bytes beside
  its payload for frames.
- `IsolatedRuntime.cs`: what generated code targets. `IIsolatedRuntime` is the plugin process's way out (calls,
  one-ways, lending a callback, mirrored reads); `IIsolatedCallbacks` is the trusted side's way back (calls,
  one-ways, synchronous callbacks by crossing class, factories as surfaces); `IsoPayload`, `IsoArgs` and `IsoObject`
  write and read arguments; `IsolationPending` is the exception a pending member throws.
- `PluginHostContextMembers` and `PluginHostContextDispatcher`, generated by the isolation generator
  (`SharpRailIsolation` = `trusted-host`): the host context's member table, its hash and the dispatcher, which has no
  member yet because every host member is pending. `IsolationMember` is one entry. `RunnerSession.StartAsync` refuses a runner
  whose `Hello` carries other tables' hash when the caller names the hash it expects.

## Boundary

- References `SharpRail.Wire` and the plugin API's host half (`SharpRail.Plugins.Api.Host`, which brings the root
  API), so no Avalonia and no host. Its internals are visible to the checks, which drive the Unix transport directly.
  Host.Core composes it behind `PluginHostSeams.Isolation`, which no shipping composition sets yet.
- NativeAOT code: no reflection; the handshake records go through a source-generated JSON context.
- Pending, in the design's terms: the host dispatcher's members and callback proxies (with the host-mode runner,
  slice 4),
  a copy of the UI member table and argument schemas without Avalonia for the relay (slice 14; today the UI table
  lives in `SharpRail.Plugins.Isolation.UI`, so the host checks only the host half of the runner's hash and the
  client the UI half, and the client's dispatcher checks a session's calls against the table), grants and the broker (slices 10 to 13), sandboxes (slices 7 to 9),
  packaging (slice 6).

## Checks

`--plugin-channel` (also a gate case) covers the codec, protocol violations against the loopback, descriptors sent
beside an unfinished frame on the Unix transport, and the runner's `probe echo` and `probe avalonia-private` modes,
including the tables' hash in `Hello`, the refusal of a runner with another, and a child of the runner that does not
hold its channel. `--plugin-isolated-ui` runs the outsider fixture in `plugin` mode through the host and the app,
and `--plugin-surface` checks the tile codec, moves and the relay's caps, then its views as pixels in the app. `--plugin-crossing` (also a gate
case) pins the tables' hashes and drives the generated UI proxy and dispatcher over the real channel.
