# Repository scripts

## Responsibility

Repository-wide tooling that does not belong to one project: installing the
checkout-local SDK, building pinned native dependencies, native probes, packaging,
and on-request measurement. Scripts prepare, package or verify; they never
implement product behavior.

## Boundary

The toolchain is one manifest, `mise.toml` (with `mise.android.toml` and `mise.browser.toml`, each with a
committed `.lock` of per-platform archive checksums), and every entry point is a mise task defined there:
`build`, `restore`, `restore:update`, `audit`, `format`, `check`, `perf`, `rpc`, `dev`, `host`,
`package:macos`, `dmg`, `package:windows`, `package:android`, `package:browser`, `android`, `browser`,
`check:packaged`, `check:terminal`, `check:fsevents`, `lsp:integration` and `targets`. `scripts/mise` and `scripts/mise.cmd`
run a mise that is already on the machine as is (the user's configuration, mise's default data directory, the checkout
trusted through `MISE_TRUSTED_CONFIG_PATHS`) and otherwise the checksum-pinned mise (`mise-pinned`, generated by
`mise generate install-script`) into mise's data directory, which is what CI uses. The files in `scripts/tasks` are the tasks' implementations, each one C# file-based app (`dotnet run`) sharing the helpers in `scripts/lib`; `tool`/`tool.cmd` and
`fetch-git.sh` are the only lookup/fetch code of our own, for what mise cannot express: printing where a pinned tool is installed (and installing it when missing), and sources pinned by Git commit. NuGet restores are locked (`packages.lock.json` per project,
`nuget.org` only, `RestoreLockedMode` in `[env]`); only `restore:update` rewrites the locks, and the Android and
Browser projects are excluded from locking (see `README.md`). `benchmark.cs` with its `window-probe.m` helper (launch timing,
only when a benchmark is requested) stays outside the task set.

The artifact matrix, the one statement of which native libraries, terminal renderer and publish task each
target has, is the header comment of the tasks in `mise.toml` (`scripts/mise run targets` prints it). The
nightly and CI workflows call those tasks and nothing else: they add caching of the tool store, the
macOS retry loop around the terminal library build, signing secrets and artifact upload.

Their public surface is the task list, [scripts/README.md](README.md), `AGENTS.md` and the root
`README.md`. Native libraries belong to the project that ships them and are MSBuild targets there (see
Invariants): Merman and notifications in `Tereditor.UI.csproj`, the Ghostty libraries in
`src/Ghostty.Avalonia` (`build-native.sh`, `build-android.sh`, `build-windows.ps1`), the WASM libraries in `Tereditor.Browser.csproj` (`wasm-native.sh`) and the file
icons in the kit. The Ghostty recipes apply the checked-in texture export and scrollback memory patches to
the pinned Ghostty source. `android` uses the pinned Android SDK (`scripts/tool android-sdk`, or `ANDROID_HOME` when set),
installs its pinned packages with the pinned licence hash when they are missing, and needs a JDK 17 or 21 (the pinned one `scripts/tool jdk` prints, or `JAVA_HOME` when set), fails with a message when either is missing, and installs the `android`
workload into the SDK when absent. Recipes may depend on POSIX `sh`, Git, `shasum`, clang/Xcode tools and,
for the benchmark only, Node. They read source trees and write only to the machine-wide cache (`TEREDITOR_CACHE_DIR`), `obj`, `.bench` and
`artifacts`; never to a repo-local `.tools`. Product logic, a second source of package versions, and editing sources are forbidden.

## Invariants

Pins and checksums. Versions and archive checksums are in the lockfiles; mise verifies them on install and
CI runs with `MISE_LOCKED=1`, which fails on anything unlocked. Sources pinned by Git commit (Ghostty) are
verified against the commit hash; an unexpected revision fails. The Windows ARM64 and x64 Zig archives are
`http:zig-windows` entries because mise's Zig has no Windows ARM64 build. The .NET SDK is not checksummed
by the lock (mise installs it with Microsoft's installer); `global.json` pins its version. dmgbuild and its
Python dependencies are pinned by version in `scripts/tasks/dmg.cs` and fetched from PyPI by the locked uv, so
the lock does not checksum them either.

Store. Tools install into mise's data directory (default `~/.local/share/mise`), one directory per version, shared by every checkout and worktree of the user and found through `scripts/tool`, so there is no bootstrap step and no link in the checkout. Checkouts at the same pin share one
copy; a version bump is a new directory, so older checkouts keep working. mise downloads and extracts
into a temporary location and renames, under its own lock, so concurrent installs are safe. The SDK takes workload packs, and the workload helper serialises those
installs. The SDK is an `http:dotnet` tool (Microsoft's archives with per-platform SHA-256), so each version has its own
directory like the other tools. Store paths are versioned
by version only: a re-published archive with the same version string and a different checksum is rejected
by the lock rather than getting a new directory. `scripts/mise` clears `DOTNET_ROOT` so a foreign SDK is never mistaken for the pin.

Caches. Zig's global package cache is shared in the store (it is content-addressed and locks per entry);
per-build caches, patched source trees and objects stay in the checkout because they embed absolute paths.

Windows x64 and ARM64 use `scripts/mise.cmd run package:windows -- -RuntimeIdentifier <rid>` for
NativeAOT client/host output (linked by Visual Studio's C++ linker) and `artifacts/tereditor-win-x64.zip` or
`artifacts/tereditor-win-arm64.zip` (ARM64 output is `artifacts/windows-arm64`; it is built on an ARM64 host,
with natives cached per RID). Published checks are staged alongside the unpacked package and excluded from the
distribution zip. Publishing refuses to replace executables running from its output directory.
`windows-native.ps1` provides exclusive file locks for the Windows native builds; both libraries retain
their own build entry points and fingerprints. The Windows CI job runs the packaged `--windows` acceptance
mode. Native build success on another platform does not count as Windows runtime verification.

Native builds are MSBuild targets with `Inputs` and `Outputs`: they run when a source file, their recipe or
the lockfile is newer than the library and otherwise not at all, so a no-op build rebuilds no native code.
The items that package a library are declared outside the building target so a skipped build still packages.
The Ghostty recipe additionally keeps a fingerprint per library, since one run produces two. Libraries are
written to a `.partial` name and renamed, so an interrupted run never leaves a half-written output. The macOS
recipes are no-ops off macOS, and the Ghostty build refuses a runtime identifier for a different architecture
than the host. The Android builds run on macOS or Linux and accept only `arm64-v8a` and `x86_64`.

`package:macos` removes the previous outputs before publishing so stale files never
survive into the package, publishes the UI and host as NativeAOT binaries (`NativeAot.props`) and the checks
as self-contained ReadyToRun, and keeps exactly one canonical app bundle. The bundle's icon is
the Icon Composer document `src/Tereditor.UI/tereditor.icon`, compiled ahead of time by `scripts/mise run icon:macos`
(`xcrun actool`, Xcode 26 or newer, run by hand; the macOS 15 CI runner cannot run Xcode 26's actool) into
`src/Tereditor.UI/AppIcon/compiled`: `Assets.car`, which macOS 26 draws with the system shape and Liquid Glass, and a
`tereditor.icns` at every size for older macOS, both for macOS 12. The document is layered (a solid navy body and the
frog as its own glass layer), so the catalog carries light, dark and tintable renderings and macOS 26 draws the icon in
each "Icon & widget style" (Default, Dark, Clear, Tinted). Packaging only copies them into the bundle and fails
when `tereditor.icon.sha256` there does not match the document, so stale outputs cannot ship. On macOS `native` wraps its
publish output in `artifacts/native/tereditor.app` with the same layout, Info.plist, icon, restamp and ad-hoc signature (one
shared helper in `scripts/lib/Tasks.cs`), and starts `Contents/MacOS/tereditor` inside it directly, so the terminal keeps the
app's output while the Dock draws the bundle's icon in the user's style. An unbundled run (`dev`) sets
`src/Tereditor.UI/Assets/AppIcon/macos.png` as its Dock icon at runtime instead, which can show only the default style: the 1024 px rendering of that document
(system shape, margin, rim highlight and drop shadow, so it matches other Dock icons), checked in and regenerated by hand
after the document changes with `iconutil -c iconset -o <dir> src/Tereditor.UI/AppIcon/compiled/tereditor.icns`,
copying `<dir>/icon_512x512@2x.png` over it; the Windows executable carries the same image as
`src/Tereditor.UI/tereditor.ico`, the Android launcher icon (every build of it) is an adaptive icon (`mipmap-anydpi-v26/icon.xml`: the navy-to-teal gradient
`drawable/icon_background.xml`, the frog `mipmap-*/icon_foreground.png` and a themed-icon `icon_monochrome.png`), with the round
`src/Tereditor.Android/icon-source.png` scaled with `sips` into `mipmap-*/icon.png` as the fallback below Android 8; the frog layers are
regenerated by `uv run --with pillow --with numpy --with scipy python3 -I scripts/android-icon-foreground.py`, which keys the frog out of `icon-source.png`, and the Linux and browser icons are the transparent logo (`brand.png`). Replacing that
bundle while the app runs is the caller's responsibility to rule out first.
Windows and Linux packaging and the profiling publisher publish the same NativeAOT binaries. Linux links them
with the pinned Zig against glibc 2.31 (`scripts/aot-linux-cc.sh`), from a Linux or macOS host; the process-group
helpers of the agent plugins compile through the same script. The packaged check stage never replaces a shipped
file; the checks only add their own, and the gate names the checks' publish so it can require each payload to
carry what that publish has for it.

`dmg` packs that bundle, unchanged and with an Applications shortcut beside it, into a compressed disk
image (`artifacts/tereditor.dmg` unless a path is given). Opened, the image shows a compact Finder window
(540 by 380 points, no toolbar, sidebar, path bar or status bar) with 128-point icons: the app on the left,
Applications on the right, and between them an arrow in the icon's navy and teal over a pale blue-grey gradient,
with a one-line hint below. The background stays light because Finder draws the labels in the viewer's text
colour, which the window settings cannot change. The background is committed at 1x and 2x (`scripts/dmg`, drawn
by `background.py`) and combined into one TIFF, so it is sharp on Retina displays; it and the volume icon (the
app icon) are dot-files, hidden in the window. The window settings live in `scripts/dmg/settings.py`; the pinned
dmgbuild, run through the pinned uv, writes the `.DS_Store` itself and attaches the image without showing it, so
building the image opens no window and needs no Finder. The image is ad-hoc signed like the bundle and not
notarized. `.github/workflows/nightly.yml` builds it on a macOS runner, the Android package on a Linux
one and the Windows x64 and ARM64 packages on Windows runners every day at 03:00 UTC (and on demand), each uploaded as a workflow artifact named
`tereditor-nightly-<date>-<commit>`. When all succeed it replaces the `nightly` prerelease: the tag moves to
the built commit and the files keep the names `tereditor-nightly.dmg`, `tereditor-nightly.apk` and the two Windows ZIPs.

`package:android` signs with the key named by `TEREDITOR_ANDROID_KEYSTORE`, `TEREDITOR_ANDROID_KEY_ALIAS` and
`TEREDITOR_ANDROID_KEY_PASSWORD` (one password for the store and the key, passed to the build by name rather
than by value); without them the package carries the machine's debug key. The nightly uses one key, kept in
the repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`, so each
night's package installs over the last. Replacing that key breaks updating from every earlier package.

The benchmark refuses to run off AC power and measures process-tree memory and
readiness markers, not synthetic timers; it is never part of the check gate.

## Conformance gates

The dependency-boundary check and the public-surface check are repository gates rather than product
behavior, but they need the compiled assemblies and negative fixtures, so they live in the checks executable
(`-- --conformance`, also in the argument-free gate) and are specified in
[the checks spec](../tests/Tereditor.Checks/SPEC.md#conformance). No script duplicates them.

`check:fsevents` is a macOS-only functional resource-lifetime check. It builds strict Release unless
`--no-build` is requested, compiles the checks' native interposer with warnings as errors, and scopes
DYLD injection to its own checks process. It rejects an existing injection and cleans its fixtures
and generated library on exit. It never modifies a running app or measures global pool occupancy.

The Android native build also stages a pinned Tailscale userspace node through
`build-tailscale-android.sh` for both packaged ABIs, with checksum-verified local Go,
the checkout NDK and module checksums. The resulting native library and dependency
license notices are included in the APK; no global Go installation is modified.

The browser build runs `build-tailscale-wasm.sh` (also `scripts/mise run tailscale:wasm`) when its inputs change.
It builds the browser's lazily downloaded Tailscale node for js/wasm with the same pinned Go and omitted-feature
tags, writes its Brotli sidecar, Go's `wasm_exec.js`, licence notices and `manifest.json`, and caches the result
under `$TEREDITOR_CACHE_DIR/tailscale-wasm/<key>` before copying it to `src/Tereditor.Browser/obj/tailscale-wasm`.
