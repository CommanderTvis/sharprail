# Repository scripts

Upstream: scripts/SPEC.md (revision: [STATUS.md](../STATUS.md#upstream-tracking))

## Responsibility

Repository-wide tooling that does not belong to one project: installing the
checkout-local SDK, building pinned native dependencies, native probes, packaging,
and on-request measurement. Scripts prepare, package or verify; they never
implement product behavior.

## Boundary

The toolchain is one manifest, `mise.toml` (with `mise.android.toml` and `mise.browser.toml`, each with a
committed `.lock` of per-platform archive checksums), and every entry point is a mise task defined there:
`build`, `restore`, `restore:update`, `audit`, `format`, `check`, `perf`, `rpc`, `dev`, `host`,
`package:macos`, `dmg`, `package:windows`, `package:android`, `package:browser`, `android`, `browser`,
`check:packaged`, `check:terminal`, `check:fsevents` and `targets`. `scripts/mise` and `scripts/mise.cmd`
run a mise that is already on the machine as is (the user's configuration, mise's default data directory, the checkout
trusted through `MISE_TRUSTED_CONFIG_PATHS`) and otherwise the checksum-pinned mise (`mise-pinned`, generated by
`mise generate install-script`) into mise's data directory, which is what CI uses. The files in `scripts/tasks` are the tasks' implementations; `tool`/`tool.cmd` and
`fetch-git.sh` are the only lookup/fetch code of our own, for what mise cannot express: printing where a pinned tool is installed (and installing it when missing), and sources pinned by Git commit. NuGet restores are locked (`packages.lock.json` per project,
`nuget.org` only, `RestoreLockedMode` in `[env]`); only `restore:update` rewrites the locks, and the Android and
Browser projects are excluded from locking (see `README.md`). `benchmark.mjs` with its `window-probe.m` helper (launch timing,
only when a benchmark is requested) stays outside the task set.

The artifact matrix, the one statement of which native libraries, terminal renderer and publish task each
target has, is the header comment of the tasks in `mise.toml` (`scripts/mise run targets` prints it). The
nightly and CI workflows call those tasks and nothing else: they add caching of the tool store, the Java
and Android SDK setup, the macOS retry loop around the terminal library build, signing secrets and artifact
upload.

Their public surface is the task list, [scripts/README.md](README.md), `AGENTS.md` and the root
`README.md`. Native libraries belong to the project that ships them and are MSBuild targets there (see
Invariants): Merman and notifications in `SharpRail.UI.csproj`, the Ghostty libraries in
`src/Ghostty.Avalonia` (`build-native.sh`, `build-android.sh`, `build-windows.ps1`), the WASM libraries in `SharpRail.Browser.csproj` (`wasm-native.sh`) and the file
icons in the kit. The Ghostty recipes apply the checked-in texture export and scrollback memory patches to
the pinned Ghostty source. `android` needs the Android SDK (`ANDROID_HOME`, default `~/Library/Android/sdk`)
and a JDK 17 or 21 (the pinned one `scripts/tool jdk` prints, or `JAVA_HOME` when set), fails with a message when either is missing, and installs the `android`
workload into the SDK when absent. Recipes may depend on POSIX `sh`, Git, `shasum`, clang/Xcode tools and,
for the benchmark only, Node. They read source trees and write only to the machine-wide cache (`SHARPRAIL_CACHE_DIR`), `obj`, `.bench` and
`artifacts`; never to a repo-local `.tools`. Product logic, a second source of package versions, and editing sources are forbidden.

## Invariants

Pins and checksums. Versions and archive checksums are in the lockfiles; mise verifies them on install and
CI runs with `MISE_LOCKED=1`, which fails on anything unlocked. Sources pinned by Git commit (Ghostty) are
verified against the commit hash; an unexpected revision fails. The Windows ARM64 and x64 Zig archives are
`http:zig-windows` entries because mise's Zig has no Windows ARM64 build. The .NET SDK is not checksummed
by the lock (mise installs it with Microsoft's installer); `global.json` pins its version.

Store. Tools install into mise's data directory (default `~/.local/share/mise`), one directory per version, shared by every checkout and worktree of the user and found through `scripts/tool`, so there is no bootstrap step and no link in the checkout. Checkouts at the same pin share one
copy; a version bump is a new directory, so older checkouts keep working. mise downloads and extracts
into a temporary location and renames, under its own lock, so concurrent installs are safe. The SDK takes workload packs, and `workload.sh` serialises those
installs. The SDK is an `http:dotnet` tool (Microsoft's archives with per-platform SHA-256), so each version has its own
directory like the other tools. Store paths are versioned
by version only: a re-published archive with the same version string and a different checksum is rejected
by the lock rather than getting a new directory. `scripts/mise` clears `DOTNET_ROOT` so a foreign SDK is never mistaken for the pin.

Caches. Zig's global package cache is shared in the store (it is content-addressed and locks per entry);
per-build caches, patched source trees and objects stay in the checkout because they embed absolute paths.

Windows x64 and ARM64 use `scripts/mise.cmd run package:windows -- -RuntimeIdentifier <rid>` for
self-contained ReadyToRun client/host output and `artifacts/SharpRail-win-x64.zip` or
`artifacts/SharpRail-win-arm64.zip` (ARM64 output is `artifacts/windows-arm64`; it is built on an ARM64 host,
with natives cached per RID). Published checks are staged alongside the unpacked package and excluded from the
distribution zip. Publishing refuses to replace executables running from its output directory.
`windows-native.ps1` provides exclusive file locks for the Windows native builds; both libraries retain
their own build entry points and fingerprints. The Windows CI job runs the packaged `--windows` acceptance
mode. Native build success on another platform does not count as Windows runtime verification.

Native builds are MSBuild targets with `Inputs` and `Outputs`: they run when a source file, their recipe or
the lockfile is newer than the library and otherwise not at all, so a no-op build rebuilds no native code.
The items that package a library are declared outside the building target so a skipped build still packages.
The Ghostty recipe additionally keeps a fingerprint per library, since one run produces two. Libraries are
written to a `.partial` name and renamed, so an interrupted run never leaves a half-written output. The macOS
recipes are no-ops off macOS, and the Ghostty build refuses a runtime identifier for a different architecture
than the host. The Android builds run on macOS or Linux and accept only `arm64-v8a` and `x86_64`.

`package:macos` removes the previous outputs before publishing so stale files never
survive into the package, publishes self-contained composite ReadyToRun UI/host and non-composite
ReadyToRun checks, and keeps exactly one canonical app bundle. Replacing that
bundle while the app runs is the caller's responsibility to rule out first.
Windows packaging and the profiling publisher use composite ReadyToRun as well. The packaged
check stage keeps shipped composite components; only newer versions of the same framework
assembly may replace shipped dependencies. The macOS harness remains non-composite so its
code can bind to the shipped composite's layouts rather than a separately compiled version
bubble. Windows checks run beside their own published components and remain composite.

`dmg` packs that bundle, unchanged and with an Applications shortcut beside it, into a compressed disk
image (`artifacts/SharpRail.dmg` unless a path is given). The image is ad-hoc signed like the bundle and not
notarized. `.github/workflows/nightly.yml` builds it on a macOS runner, the Android package on a Linux
one and the Windows x64 and ARM64 packages on Windows runners every day at 03:00 UTC (and on demand), each uploaded as a workflow artifact named
`SharpRail-nightly-<date>-<commit>`. When all succeed it replaces the `nightly` prerelease: the tag moves to
the built commit and the files keep the names `SharpRail-nightly.dmg`, `SharpRail-nightly.apk` and the two Windows ZIPs.

`package:android` signs with the key named by `SHARPRAIL_ANDROID_KEYSTORE`, `SHARPRAIL_ANDROID_KEY_ALIAS` and
`SHARPRAIL_ANDROID_KEY_PASSWORD` (one password for the store and the key, passed to the build by name rather
than by value); without them the package carries the machine's debug key. The nightly uses one key, kept in
the repository secrets `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEY_ALIAS` and `ANDROID_KEY_PASSWORD`, so each
night's package installs over the last. Replacing that key breaks updating from every earlier package.

The benchmark refuses to run off AC power and measures process-tree memory and
readiness markers, not synthetic timers; it is never part of the check gate.

## Conformance gates

The dependency-boundary check and the public-surface check are repository gates rather than product
behavior, but they need the compiled assemblies and negative fixtures, so they live in the checks executable
(`-- --conformance`, also in the argument-free gate) and are specified in
[the checks spec](../tests/SharpRail.Checks/SPEC.md#conformance). No script duplicates them.

`check:fsevents` is a macOS-only functional resource-lifetime check. It builds strict Release unless
`--no-build` is requested, compiles the checks' native interposer with warnings as errors, and scopes
DYLD injection to its own checks process. It rejects an existing injection and cleans its fixtures
and generated library on exit. It never modifies a running app or measures global pool occupancy.

The Android native build also stages a pinned Tailscale userspace node through
`build-tailscale-android.sh` for both packaged ABIs, with checksum-verified local Go,
the checkout NDK and module checksums. The resulting native library and dependency
license notices are included in the APK; no global Go installation is modified.
